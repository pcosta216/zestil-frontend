## 2026-09-29 — Migrated into the `docs/AGENT_DOCS_STRUCTURE.md` folder convention

Prompted directly by a request to document the recipe parser. `RECIPE_PARSER_DESIGN.md` already existed and was recent and detailed, so this was a migration-and-verify pass, not a from-scratch read — but every claim in it was checked against live code before being carried into `SPEC.md`, not copied on trust.

**Verified still accurate, not just carried over:** `git log --since=2026-08-23` on all four core modules (`recipe_parser.py`, `full_recipe_parser.py`, `instruction_parser.py`, `recipe_save.py`) returns zero commits — none of them have changed since the prior doc's snapshot date. The two specific line-numbered claims spot-checked directly against current `app/db.py` (`insert_recipe_lines` at `:959`, `resolve_waitlist_for_ingredient` at `:1075`) still match exactly, despite `db.py` itself having three unrelated commits in that window (a `commit()` method addition and two others, none touching recipe ingestion). The "known gaps" list was re-checked, not assumed: `app/recipe_reader.py` and `app/ingredient_conversion.py` still exist and still `import supabase_connection`, a module still absent from the tree — the dead-code claim holds.

**One real correction: §9's "Three entry points" table was incomplete, not just outdated.** The prior doc named `/api/v1/recipe/parse`, `/api/v1/recipe/submit`, and the dashboard flow — but `app/api.py` has always also had `POST /api/v1/recipe/save` (added `58dd1a1`, 2026-05-07) and `POST /api/v1/recipe/link` (added `dcbfa58`, 2026-05-08), both well before the prior doc's 2026-08-23 snapshot. This wasn't a since-added feature the old doc predates — it was an omission in that doc from the start. `SPEC.md` §3 now lists all four HTTP routes plus both dashboard flows (the dashboard's ingredients-only `/database/recipe-parse` flow was also missing from the old doc's coverage). Grepped `supabase/functions/` and `app/` for any caller of `/recipe/link` or `/recipe/save` — none found; recorded as an open question in `SPEC.md` §3 rather than assumed unused, since a caller could exist in `zestil-frontend`, which isn't in this workspace.

**Migration file paths corrected.** The prior doc cited migration files by bare name (`20260504_unit_map.sql`, etc.) — the migrations directory has since been reorganized into year-month subdirectories; all four files this doc references now live under `supabase/migrations/202605/`. `SPEC.md`'s citations were updated to the real current paths.

**Slug deliberately does not end in `-agent`.** `docs/AGENT_INVENTORY.md` itself puts this parser in its own subsection (§5, "Parsers (LLM-assisted, deterministic-first)"), explicitly separate from the table of Python/Flask *agents* directly above it, and the fleet's own headline count ("12 distinct LLM agents actually doing work today") does not include it. Naming this folder `recipe-parser-agent` — matching the pattern used for `nutrition-research-agent` and `completion-agent` — would misrepresent something the repo's own inventory deliberately classifies as plumbing, not one of the fleet's agents. `recipe-parser` was used instead, matching how the module files themselves are named.

**Real finding surfaced during this pass, not previously tracked: `app/api.py`'s `X-User-Id` header is trusted with no session verification, and two routes need no `X-API-Key` either.** While writing `SPEC.md` §8's auth section, checked whether anything in `app/api.py` verifies `X-User-Id` against a real session (the same class of gap `docs/VULNERABILITIES.md` finding #2 already tracks for `optimize-day-agent`) — grepped the whole file for any JWT/auth import; there is none. Every one of the five routes reading `X-User-Id` (`recipe/submit`, `recipe/link`, `recipe/save`, `plan_chat`, `chat_stream`) takes it verbatim. Two of those five — `POST /api/v1/plan` and `POST /api/v1/chat` — don't check `X-API-Key` at all, so they need no secret whatsoever, just a non-empty `X-User-Id` value, to act as an arbitrary user. Logged as [`VULNERABILITIES.md` finding #12](../VULNERABILITIES.md#12-app_apipys-x-user-id-header-is-trusted-with-no-session-verification-and-two-routes-need-no-secret-at-all). Separately, while confirming which routes finding #8's leaked `API_KEY` actually gates, found that its stated impact (naming only `/research-ingredient` and `/weblookup-ingredient`) undersells its own blast radius — the same `api_key != API_KEY` check also gates all three parse/submit/save recipe routes (`/recipe/parse` needs no `X-User-Id` but does need this key). Appended a scope-correction note to finding #8 rather than rewriting its original text, per this file's own no-rewrite rule extended to that document.

No other new security/privacy gap was found while cross-checking this subsystem against `VULNERABILITIES.md`'s existing entries.
