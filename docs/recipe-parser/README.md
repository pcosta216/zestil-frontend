# Recipe Parser — Documentation

Turns a recipe — raw pasted text or a URL to scrape — into structured, database-backed data: ingredient lines resolved against the ingredient catalog (`fdcid_uuid`, so macros can actually be computed), a list of instruction steps, and recipe metadata. Four Python modules working together (`full_recipe_parser.py`, `recipe_parser.py`, `instruction_parser.py`, `recipe_save.py`), reachable through four HTTP routes and two dashboard flows. Feeds [`AGENT_INVENTORY.md`](../AGENT_INVENTORY.md)'s W5 (recipe ingestion) workflow, and hands off anything it can't resolve to the balancing/database-agent self-healing loop.

This folder follows the standard structure described in [`docs/AGENT_DOCS_STRUCTURE.md`](../AGENT_DOCS_STRUCTURE.md) — read that first if you haven't seen this convention before.

**Deviations from the standard template, and why:**

- **Not one of the fleet's agents — deliberately not named `recipe-parser-agent`.** `docs/AGENT_INVENTORY.md` itself puts this in its own subsection (§5, "Parsers (LLM-assisted, deterministic-first)"), separate from the Python/Flask agents table directly above it, and its own headline count of "12 distinct LLM agents actually doing work today" doesn't include it — most of this pipeline is deterministic code; only two calls (name extraction, disambiguation) are open-ended LLM calls, and both are constrained to return an index into a list rather than free-form output. The slug is `recipe-parser`, matching the module names, not the `-agent` pattern used for `nutrition-research-agent`/`completion-agent`.
- **Not a Supabase Edge Function — the slug doesn't point at a real deployed directory.** Same deviation as [`nutrition-research-agent`](../nutrition-research-agent/README.md): this is a Python/Flask module under `app/`, orchestrated inside the same Flask app as every other Python agent in this repo. There is no `supabase/functions/recipe-parser/` directory.
- **No `TOOLS.md`.** Both open-ended LLM calls (name extraction, disambiguation) are fixed, single-purpose calls with a hand-written schema — not a model-driven tool-selection loop.
- **No `CONTRACT.md`/`FRONTEND.md`.** All four HTTP routes are called with a static internal `X-API-Key`, not a per-user frontend session — there's no frontend-team contract to publish against. (This *is* the auth pattern flagged as a real gap in `SPEC.md` §8 and `VULNERABILITIES.md` finding #12 — the absence of a session-level contract is exactly the problem, not a reason to skip documenting one.)
- **Covers `recipe_save.py`'s persistence and self-healing loop, not just the two parsing modules.** `docs/AGENT_INVENTORY.md`'s "Parsers" bullet list names only `recipe_parser.py`, `instruction_parser.py`, and `full_recipe_parser.py` by file — but parse → save → waitlist → self-heal is one continuous, deliberately-connected pipeline (an unmatched line only makes sense in light of what happens to it after save), and the prior flat doc already covered persistence in its own §8. Splitting it into a separate document would sever a single design story into two.
- **One `SPEC.md` covers four HTTP routes and two dashboard flows**, rather than one document per entry point — all six are thin wrappers around the same two functions (`parse_recipe`/`parse_full_text`/`scrape_and_parse_full`, and `save_full_recipe`); the interesting behavior lives in those functions, not in which route calls them.

**Status:** live, in production use — this is the `full_recipe_parser`/`save_full_recipe` pair `AGENT_INVENTORY.md`'s W5 workflow depends on for all recipe ingestion.
